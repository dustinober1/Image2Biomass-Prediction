### Task 1: Create ResourceManager for GPU/CPU Detection and Allocation

**Type:** auto

**Files:**
- `mlflow_tracking/resource_manager.py`

**Action:**
Create ResourceManager class with the following capabilities:

1. **GPU Detection:**
   - Detect available GPUs using `torch.cuda.is_available()` and `torch.cuda.device_count()`
   - Fallback to `nvidia-smi` command via subprocess if PyTorch not available
   - Return list of GPU IDs (e.g., [0, 1, 2, 3] for 4-GPU system)
   - Get GPU memory info via `torch.cuda.get_device_properties()` or nvidia-smi
   - Handle gracefully when no GPUs available (return empty list)

2. **CPU Detection:**
   - Use `os.cpu_count()` to get available CPU cores
   - Reserve 1-2 cores for system processes (configurable via reserve_cores parameter)
   - Return available cores for experiment execution

3. **Resource Availability Check:**
   - `can_allocate(gpu_count=0, cpu_cores=1)` -> bool
   - Check if requested GPUs and CPU cores are available
   - For GPUs: check if device_count >= requested gpu_count
   - For CPUs: check if (cpu_count - reserve_cores) >= requested cpu_cores

4. **Resource Tracking:**
   - Track allocated resources to prevent over-subscription
   - `allocate(gpu_id=None, cpu_cores=1)` -> ResourceToken (with context manager support)
   - `deallocate(token)` releases resources
   - Thread-safe allocation using threading.Lock

5. **Auto-scaling Recommendations:**
   - `suggest_concurrent_experiments(gpus_per_exp=0, cpu_per_exp=1)` -> int
   - Calculate max concurrent experiments based on available resources
   - For GPU experiments: min(available_gpus // gpus_per_exp, available_cpus // cpu_per_exp)
   - For CPU-only experiments: available_cpus // cpu_per_exp

**Implementation Notes:**
- Use singleton pattern for ResourceManager (only one instance needed)
- Handle missing PyTorch gracefully (try/except ImportError)
- Use context managers for resource allocation (RAII pattern)
- Provide `get_resource_summary()` -> dict with current allocation state

**Verification:**
```python
# Test GPU detection
rm = ResourceManager()
gpus = rm.get_available_gpus()  # Returns list of GPU IDs or []
print(f"Available GPUs: {gpus}")

# Test CPU detection
cpus = rm.get_available_cores(reserve_cores=2)
print(f"Available CPUs: {cpus}")

# Test allocation
if rm.can_allocate(gpu_count=1):
    with rm.allocate(gpu_id=0, cpu_cores=4) as token:
        print(f"Allocated: {token}")
        # Run experiment
    # Resources automatically released
```

**Done:**
- ResourceManager can detect available GPUs and CPUs
- ResourceManager.can_allocate() correctly checks resource availability
- ResourceManager.allocate() returns context manager for resource management
- ResourceManager.suggest_concurrent_experiments() provides safe concurrency limits
- All methods handle missing GPUs gracefully (no crashes)

### Task 2: Create BatchExecutor for Parallel Experiment Execution

**Type:** auto

**Files:**
- `mlflow_tracking/batch_executor.py`

**Action:**
Create BatchExecutor class with the following capabilities:

1. **Batch Configuration Loading:**
   - `load_configs(config_paths: List[str])` -> List[ExperimentConfig]
   - `load_configs_from_dir(dir_path: str, pattern="*.yaml")` -> List[ExperimentConfig]
   - Use ConfigParser.load_config() for each file
   - Handle invalid configs with warnings (skip, don't fail entire batch)

2. **Parallel Execution Engine:**
   - `execute_batch(configs: List[ExperimentConfig], max_workers: Optional[int] = None)` -> List[ExperimentResult]
   - Use `concurrent.futures.ThreadPoolExecutor` for I/O-bound experiments (script execution)
   - Use `concurrent.futures.ProcessPoolExecutor` for CPU-bound experiments (optional, via flag)
   - Limit concurrency via max_workers (auto-suggest from ResourceManager if None)
   - Execute each config using existing adapter pattern (AdapterRegistry)

3. **Resource-Aware Scheduling:**
   - Integrate ResourceManager for GPU allocation
   - Before execution, check if resources available via ResourceManager.can_allocate()
   - Pass GPU ID to config via `config.parameters['gpu_id']` (adapters must use it)
   - Wait for resources if all GPUs busy (configurable timeout)
   - Release GPU after experiment completes

4. **Progress Monitoring:**
   - Real-time progress updates: "Running 3/10 experiments (2 completed, 1 failed, 0 running)"
   - Track experiment status: pending, running, completed, failed
   - Show active experiments with run IDs
   - Optional verbose mode for detailed per-experiment output

5. **Error Handling:**
   - Failed experiments don't block others (try/except per experiment)
   - Collect errors in ExperimentResult.status = "failed"
   - Log error messages to MLflow via tracker.mark_failed()
   - Return partial results if some experiments fail

6. **Result Collection:**
   - ExperimentResult dataclass with: run_id, status, metrics, error, config
   - Return list of ExperimentResult in same order as input configs
   - Aggregate metrics across batch (e.g., "Best val.rmse: 8.2 from run_id=abc")

**Implementation Notes:**
- Use ThreadPoolExecutor (not ProcessPoolExecutor) for simplicity (subprocess already provides isolation)
- Limit concurrency to ResourceManager.suggest_concurrent_experiments() by default
- Pass gpu_id parameter to scripts (adapters must support it)
- Use `as_completed()` from concurrent.futures to process results as they finish
- Provide callback hooks for custom progress reporting (on_start, on_complete, on_error)

**Verification:**
```python
# Test batch execution
executor = BatchExecutor()
configs = executor.load_configs_from_dir("examples/configs/batch/")

results = executor.execute_batch(
    configs,
    max_workers=4,  # Run up to 4 experiments in parallel
    verbose=True
)

for result in results:
    print(f"{result.config.run_name}: {result.status}")
    if result.status == "completed":
        print(f"  val.rmse: {result.metrics.get('val.rmse')}")
```

**Done:**
- BatchExecutor.load_configs() loads multiple YAML configs into ExperimentConfig list
- BatchExecutor.load_configs_from_dir() discovers and loads all YAML configs in directory
- BatchExecutor.execute_batch() runs experiments in parallel with ThreadPoolExecutor
- BatchExecutor respects max_workers limit (defaults to ResourceManager suggestion)
- BatchExecutor monitors and reports progress (X/Y completed, Z failed)
- Failed experiments don't block other experiments (isolated error handling)
- BatchExecutor returns ExperimentResult list with status, metrics, and errors

### Task 3: Extend CLI for Batch Execution

**Type:** auto

**Files:**
- `mlflow_tracking/cli.py` (modify)

**Action:**
Extend CLI with batch execution command:

1. **New `exp-run-batch` Command:**
   - Accept `--dir` parameter for batch directory (instead of single config)
   - Accept `--configs` parameter for multiple config files (comma-separated)
   - Accept `--max-workers` parameter for concurrency limit (optional, auto-suggest if not provided)
   - Accept `--verbose` flag for detailed progress output
   - Usage: `exp-run-batch --dir examples/configs/batch/ --max-workers 4`

2. **BatchExecutor Integration:**
   - Import BatchExecutor and ResourceManager
   - If `--dir` provided: use `executor.load_configs_from_dir(args.dir)`
   - If `--configs` provided: parse comma-separated list, use `executor.load_configs(config_paths)`
   - Call `executor.execute_batch(configs, max_workers=args.max_workers, verbose=args.verbose)`
   - Print summary after completion: "Completed 8/10 experiments (2 failed)"

3. **Resource Summary:**
   - Before execution, print resource availability:
     ```
     Available Resources:
       GPUs: 1 (0 allocated)
       CPUs: 8 (2 reserved for system)
     Max concurrent experiments: 4
     ```
   - Use ResourceManager.get_resource_summary() for this output

4. **Exit Codes:**
   - 0: All experiments completed successfully
   - 1: Some experiments failed (but batch completed)
   - 2: Batch execution error (no configs loaded, etc.)
   - 3: Resource allocation error (insufficient resources)

5. **Error Handling:**
   - Handle batch execution errors gracefully
   - Print summary of failed experiments with error messages
   - Don't raise exceptions for individual experiment failures (logged to MLflow)

**Implementation Notes:**
- Reuse existing argparse setup in main()
- Create separate function `exp_run_batch_command()` for batch execution
- Export new function from __init__.py
- Add entry point in setup.py: `exp-run-batch = mlflow_tracking.cli:main_batch`

**Done:**
- `exp-run-batch` command accepts `--dir` or `--configs` for batch execution
- CLI integrates with BatchExecutor for parallel execution
- CLI prints resource summary before batch execution
